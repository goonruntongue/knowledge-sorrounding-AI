DEPLOY / CHOOSE / WEB

ウェブアプリの
公開先を選ぶ。

サービス名から選ぶ前に、まず「何を作るか」と「どの部品が必要か」を整理します。デプロイとは、作ったものを使えるようにすること。
Webアプリに関して言えば、インターネットで使えるように公開することです。

01 / デプロイとは？

完成したものを、使える場所へ置く。

パソコンの中だけで動く制作物を、URLから誰でも（または許可した人だけが）使える状態にすることです。画面だけ公開できても、必要な部品がなければアプリは動きません。

FRONTEND

画面。HTML / CSS / JavaScript

BACKEND

API、認証、メール、権限制御

DATABASE

ユーザー、投稿、履歴、設定

STORAGE

画像、動画、PDF、添付

選ぶ基準：特に重要なのは「バックエンドで何を実行したいか」です。既存PHP、JavaScript/TypeScriptのAPI、常駐Node.jsでは向く場所が変わります。

02 / 実際にデプロイする時の選択肢

同じ公開でも、提供の形が違う。

XaaS は「必要な仕組みをサービスとして借りる」考え方です。サーバーを自分で管理する度合いで分けます。

PaaS

アプリを動かす土台を借りる

Cloudflare Workers、Vercel Functions、Renderなど。OS管理を減らし、コードの公開に集中します。

BaaS

アプリの裏側の完成部品を借りる

Firebase、Supabaseなど。認証・DB・ストレージ・リアルタイム機能を組み合わせます。

IaaS

仮想サーバーを借りる

VPSやクラウドVM。PHP、Node.js、Python、Socket.IOなどを自由に動かせますが、保守も担当します。

SHARED HOSTING

既成のWebサーバーを借りる

一般的なレンタルサーバー。既存PHPフォームやWordPressを大きく変えずに公開できます。

03 / 用途から選ぶ

作りたいものを、必要な部品に分ける。

目的必要な構成主な候補
Webサイトを公開するフロントエンドのみCloudflare Pages、Netlify、Vercel、Firebase Hosting、レンタルサーバー
お問合せフォーム付き画面 + 送信を受ける処理新規JS/TSならCloudflare Workers、簡易フォームならNetlify Forms、既存PHPならレンタルサーバー
掲示板・コメント画面 + APIまたはBaaS + DBSupabase、Firebase、Cloudflare Workers + D1
ログイン・チャット画面 + 認証 + リアルタイム + DBCloudflare Workers + Durable Objects + D1、Firebase、Supabase、VPS

04 / プラットフォームの特徴

得意な仕事と、そのまま移せないもの。

サービス得意なこと注意点
Cloudflare静的サイト、API、フォーム、軽いバックエンド、WebSocket既存PHPや通常の常駐Node.jsをそのまま実行する用途ではない
Firebase認証、Firestore / Realtime Database、通知、WebアプリSecurity Rulesの設計と利用量の確認が重要
SupabasePostgreSQL、認証、ファイル、Realtimeフロントエンドの公開先は別途用意する構成が自然
Netlify / Vercel静的サイト、Git連携、プレビュー、関数常駐型リアルタイムサーバーをそのまま置く用途には向かない
レンタルサーバー / VPS既存PHP / WordPress、または自由なサーバー実行VPSは更新・セキュリティ・バックアップも担当する

05 / ウェブアプリのデプロイのやり方

先に構成を決めてから、公開の手順へ。

  1. 用途を一文で書く。 例：「ログインした人が画像付きの投稿を残せる掲示板」。
  2. 必要な部品を選ぶ。 画面だけか、API・認証・DB・ストレージ・リアルタイムが必要かを確認します。
  3. 既存コードの条件を確認する。 PHPをそのまま使うか、JS/TSに作り直せるか、常駐Node.jsが必要かを分けます。
  4. 公開先を一つ決め、小さく試す。 画面を公開し、必要な部品を一つずつ接続します。
  5. 本番前に料金・権限・バックアップを確認する。 無料枠・請求先・公開範囲・環境変数を公式ページで確認します。
公開だけ → Cloudflare Pages 既存PHPフォームを変えたくない → 一般的なレンタルサーバー 新規フォームをJS / TSで作る → Cloudflare Workers 投稿やコメントをSQLで管理したい → Supabase 完成部品中心で早く作りたい → Firebase リアルタイムの部屋を柔軟に作りたい → Cloudflare Durable Objects 既存Node.js / Socket.IOを動かしたい → VPS または Render

06 / リアルタイム空間の考え方

動いている「今」と、残す記録を分ける。

現在座標や接続中ユーザーは、毎回DBへ保存せず、WebSocketやRealtimeで一時的に配信します。チャット履歴やプロフィールはDBに保存します。位置更新は毎秒2〜4回程度に間引き、ブラウザ側で補間します。

一時状態：接続中ユーザー、現在座標、方向 → Durable Objects / Realtime Database / Supabase Realtime 永続データ：ユーザー、部屋情報、チャット履歴、プロフィール → D1 / Firestore / PostgreSQL

二つの第一候補：部屋の状態を主役にするなら「Cloudflare Pages + Workers + Durable Objects + D1」。ログイン・プロフィール・検索などSQLデータを主役にするなら「Cloudflare Pages + Supabase」です。
